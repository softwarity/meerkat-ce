The API, and its token

{{ origin() }}/api/schedules

GET / The list, narrowed by meta.<key>, tenant, route.
GET /{id} One schedule.
POST / Create one; the id comes back.
PUT /{id} Change it.
DELETE /{id} Remove one. Its run in flight is told to stop.
POST /{id}/pause Stop it firing. Its run in flight is told to stop.
POST /{id}/resume Let it fire again.
POST /{id}/run Owe a turn now.
PATCH /{id}/run Report on a run you answered 202 to. The answer may tell you to stop.
DELETE /{id}/run Cancel the run in flight.
GET /{id}/runs What each turn did, newest first.
POST /pause?meta.<key>=... Pause every schedule the filter matches.
POST /resume?meta.<key>=... Resume every schedule the filter matches.

A token minted for it reaches only this API. What the calls may reach is set by each schedule's roles, so one token serves all your endpoints.

This is the internal plane: a port inside the cluster, never behind an ingress. What a service presents there - nothing, this token, or its pod's ServiceAccount token - is set under Access. Services write their schedules there. This console reads them, pauses, resumes, runs, cancels or deletes them, and writes only their description.

Create and replace

Or a calendar: cron, read in a timezone. One or the other, never both.

Or one date: the call goes out once, then the schedule is finished. A past date still goes out if catchUp allows it.

name Required. Shown on this screen and in logs.
description What it is for, 500 characters at most, shown under the name. An operator can write it here; a PUT without it keeps it.
roles The roles the call carries, as meerkat; the route's rule checks them. role for one, roles for several, never both. No role: only open endpoints.
routeId Required. A route id of this gateway, not a URL.
method POST by default, or PUT, PATCH, DELETE. GET is refused.
path The path on that route, starting with a slash.
headers Extra headers, ten at most. A value may be a vault reference ($name), resolved at call time and never stored. Authorization, Host and Meerkat-* are refused.
body JSON. An object or array goes out as application/json; a JSON string goes out as its content (form, XML). contentType overrides.
every An ISO 8601 duration (PT30M, PT6H, P1D), one minute at least. Counted from the end of the last run.
cron Standard five-field cron, with lists, ranges, steps, MON-SUN, JAN-DEC and @hourly, @daily, @weekly, @monthly, @yearly.
at One date, RFC 3339 with its offset (2026-10-03T04:00:00Z). Refuses timezone and startAt. Give every, cron or at, never two.
timezone IANA name for reading the cron, UTC by default. Daylight saving is followed.
metadata Your own keys and text values, twenty at most, to find schedules again. Never sent with the call.
overlap skip only: a turn due while a run is in flight waits for it to close. run is refused.
catchUp Seconds, 0 by default: how late a missed turn may still go out (only the last one). 0 means however late.
timeout ISO duration, 30 seconds by default, two minutes at most. It bounds the answer, not the work (see 202 below).
retryLost ISO duration, one minute to one day, none by default: how long after a lost run (202, then silent) the same run is sent again. Only if your service can pick its work up again.
When the endpoint is protected

Guarded by the gateway: set the roles the call needs. The service receives meerkat with them, as the route hands identity over. A wrong role shows as a 403 here.

Guarded by the service's own secret: put it in headers as a vault reference, never in clear.

Find them again

meta.<key>=<value> matches exactly, meta.<key>=~<expression> by regular expression; all conditions apply. tenant and route also filter.

What your service receives

A normal request on the application port, through the route's rules. Keep the run identifier and ignore a run you already handled: delivery is at least once.

Sent twice only if the calling gateway stops before your answer: another one resends it with the same run identifier, Meerkat-Job-Attempt counting, three attempts at most. An answer you gave is never replayed.

Long work answers 202

Answer 202 Accepted to keep the run open and report its progress, then its end. Any other answer closes it: 2xx done, the rest failed.

run Required: the Meerkat-Job-Run of the call. It is the proof, no token is needed.
state running (or nothing) while it works, done or failed to close it.
progress 0 to 100: the bar on this screen.
detail Your words. While it runs, shown live under the name (7 233 / 9 882 records, 200 characters); at the end, kept in the history.
retryIn With failed: call me back then (see below).

The answer: 204 carry on (or, at the end, recorded). 410 Gone stop: the run is already closed on our side, report nothing more. Its stop says why: paused, cancelled, deleted, lost or closed. 409: a run id you were never given.

Paused while it runs: your next progress report gets the 410 and the run closes as cancelled; the next turn comes after a resume. A final report on a paused schedule is still taken. Cancelled (here, or DELETE /{id}/run): closed at once, any later report gets the 410.

Every report renews the lease. Without one for five minutes the run is lost. It is not sent again unless the schedule says retryLost: then, after that delay, the same run is sent again (same Meerkat-Job-Run, next Meerkat-Job-Attempt), three attempts per turn at most. A report arriving meanwhile takes the run back.

When you cannot run it yet

If the work cannot be done yet, answer 424 Failed Dependency with a Retry-After (seconds or HTTP date): the turn comes back then. Not 503.

After a 202, report {{ "{" }}"state":"failed","retryIn":"PT10M"{{ "}" }}. The reason stays on the run. One minute to one day, five times in a row at most.

The history of a schedule

Every finished run is kept: when, how (done, failed, lost, cancelled, dropped when too late), the answer, the node and the attempt.

Replay a run by its id: it goes out as a new run with today's payload, and the history says which one it replays.

When a call fails

A service that is down gets a 502 and the run fails; other schedules are not affected. A call past the timeout is closed and says so.

Three attempts, then the next turn. 401, 403, 404, 502, 503, 504 or no answer are retried after 30 seconds, then 2 minutes, within catchUp. Anything else, 500 included, waits for the next turn. Each attempt is a new run.
