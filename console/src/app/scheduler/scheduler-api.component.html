The API, and its token

http://meerkat:9090/api/schedules

POST / Create one; the id comes back.
PUT /{id} Change it.
GET / The list, narrowed by your own metadata.
DELETE /{id} Remove one.
POST /{id}/pause And /resume, /run.
GET /{id}/runs What each turn did, newest first.
PATCH /{id}/run Report on a run you answered 202 to.

The token's perimeter is schedules: this API and nothing else on this port. What the calls may REACH is in the schedule, not in the token - see roles below - so one token schedules for as many different endpoints as your backend serves.

key Mint a token

Create and replace

An ordinary create: POST hands back an id, and everything else takes it. If you would rather not keep it, file the schedule under your own metadata and ask for it back that way - which is what a reconciliation loop does instead of naming its own ids.

A cadence - every so often, counted from the end of the last run:

Or a calendar - cron, read in a zone - for what a duration cannot say: every Monday at three, the first of the month, weekdays at eight. One or the other, never both.

Or one date - a delayed action. The call goes out then, once, and the schedule is finished: nothing is armed after it. That is what to post when the trigger is something that happened - a basket left behind, a booking made - rather than a position in a calendar. A date already past still goes out if catchUp allows it.

name Required. What this screen lists and what a log line says.
roles The roles the CALL carries. There is no account behind a scheduled call: it is made as meerkat holding these, and the route's rule reads them like anybody else's. Say role for one, roles for several - the same field, never both at once. No role at all and the call reaches only what is open to everyone.
routeId Required. A route of this gateway - the id, not a URL. Unknown ids are refused by name.
method The verb of the outgoing call: POST by default, and PUT, PATCH or DELETE for a service whose endpoint reads that way. GET is refused, a scheduled call being an action rather than a read nobody looks at.
path The path on that route, starting with a slash.
headers Extra headers the call carries, ten at most. A value may be a vault reference - $name - resolved at the moment of the call: the schedule keeps the reference, so the secret is never stored, never returned by this API and never drawn on this screen. Authorization is refused because on this plane it IS the account the schedule runs as, and the gateway writes it; so are Host and the Meerkat-* headers.
body JSON. An object or an array goes out as it stands, as application/json; a JSON string goes out as its content, which is how a form or an XML document is sent. An explicit contentType wins either way.
every A cadence, as an ISO 8601 duration - PT30M, PT6H, P1D. One minute is the shortest. Counted from the END of the last run, which is what keeps a slow job from firing again the instant it returns.
cron A calendar instead: the five standard fields (minute hour day-of-month month day-of-week), with lists, ranges and steps, the names MON-SUN and JAN-DEC, and the shortcuts @hourly, @daily, @weekly, @monthly, @yearly. As in every crontab, a day matching either day field is a match when both are restricted. Give every or cron, never both.
at One date instead, RFC 3339 with its offset - 2026-10-03T04:00:00Z. The call goes out then, once, and the schedule is finished. The date carries its own offset, so timezone is refused beside it, and so is startAt, which places the first turn of something that repeats. Give every, cron or at, never two.
timezone Where the calendar is read - an IANA name such as Europe/Paris, UTC by default - because "three in the morning" is a question about where. Daylight saving is followed: an hour that does not exist that morning runs at the next one, and an hour that happens twice fires once. Only a calendar has a zone; a duration is the same length everywhere.
metadata Your own filing system: any keys you like, text values, which Meerkat stores and matches on without knowing what they mean. It is how one token serves a fleet - see below. Twenty keys at most. Nothing here is sent with the call: it is how you find the schedule again, and it is also where an owner goes if you want one - "owner": "stations-svc" is a key like any other, yours to name and yours to search on.
overlap skip (the default) or run: what to do with a turn that arrives while the previous run is still in flight. Skipping lets it go: nothing more is owed until that run closes, and its close arms the next turn - so a slow job never finds one waiting in the past the instant it returns.
catchUp Seconds, 0 by default. How LATE a missed turn may still go out: a gateway down all night fires the last hourly turn on waking, or none - never twelve in a row. 3600 means "still worth doing within the hour"; 0 means whenever, however late.
timeout ISO duration, 30 seconds by default, two minutes at most. It bounds the ANSWER, not the work: that is what the 202 below is for.
When the endpoint is protected

The gateway guards it - a rule on the route, or a rule on that one endpoint - and what the schedule adds is one line: the roles the call must carry. It goes out as meerkat holding them, and your service receives that the way the route hands identity over: headers, REMOTE_USER, or a signed JWT. Ask for the wrong role and the schedule fails every night with a readable 403 on this screen - the rule is the same one that refuses a person.

The service guards it with a secret of its own - an API key, a shared token - and that is what headers is for, with a vault reference as the value. Never the secret in clear.

Find them again

meta.<key>=<value> matches exactly, meta.<key>=~<expression> by regular expression; several conditions are all required. tenant and route narrow too.

What your service receives

An ordinary request on the application port: it passed the route and its rules on the way in, carrying the roles the schedule asked for. Keep the run identifier and ignore one you have already acted on - the call is made at least once, and that header is your half of it.

When is it sent twice? Only when the gateway making the call stops before your answer comes - a crash, or a rolling deployment. Then another gateway sends it again, same run identifier, with Meerkat-Job-Attempt counting: three attempts at most, and never later than the schedule's catchUp. A gateway that stops cleanly hands its calls over at once; one that dies, after five minutes. An answer you gave is never replayed, a failure included.

Long work answers 202

The call starts the work, it does not wait for it. Answer 202 Accepted and the run stays open: you report your progress, and eventually that it is done - which is what this screen draws while it happens. Any other answer closes the run: 2xx done, the rest failed.

The 202 is also how we know the work is yours: from then on the call is never sent again, whatever happens to the gateway. Say nothing for five minutes and the lease lapses: the run closes as lost and the schedule gets its next turn, rather than staying "running" for ever. Every report renews it.

When you cannot run it yet

Sometimes nothing is broken and the work simply cannot be done yet: the extract is not published, the dependency has not answered. You know why, and you know when to come back - the gateway cannot guess either. Answer 424 Failed Dependency with a Retry-After, in seconds or as an HTTP date, and the turn comes back then. Not 503, which says "I am down" and is already covered by trying again.

For a job you accepted with a 202, the same answer goes on the report: {{ "{" }}"state":"failed","retryIn":"PT10M"{{ "}" }}. Either way the REASON you give stays on that run, and the turn that follows points back at it - the history reads "not published yet, put off to 10:15, done". A minute at the soonest, a day at the furthest, and five times in a row at most: past that the turn is let go and the schedule's own cadence takes over.

The history of a schedule

The schedule keeps the LAST result; every turn that ended is kept on its own. It is what answers "since when is this failing" and "did last night's close run": when it ended, how (done, failed, lost when you took the work and went quiet, dropped for a turn that never went out because it came round too late), what answered, which node made the call, and which attempt ended it.

A turn that was dropped, or that failed for a reason since fixed, is asked for again by name - it goes out as a NEW run with today's payload, and the history says which one it replays. This screen has the same button on each run in a schedule's drawer.

When a call fails

A service that is down gets the gateway's own 502, and the run closes as failed with the sentence that page carries. Nothing is stuck, and no other schedule is affected - each call is made on its own, so a slow service holds its own call and nobody else's. A call that outlasts the schedule's timeout is closed by us and says so, rather than blaming your service for a wait we walked away from.

Three attempts, then the next turn. A few answers are usually a moment rather than a verdict, because behind a schedule there is an internal service: 401, 403 and 404 - not known yet, roles not loaded, a version still coming up - and 502, 503, 504 or no answer at all. Those are tried again 30 seconds later, then 2 minutes later, and no more; never past the schedule's catchUp. Anything else, and 500 first of all, waits for the next turn: that is your service saying something, and it is handled where it is said. Each attempt is a NEW run with its own identifier - you never acted on the one that failed - and the history links them as one turn.
