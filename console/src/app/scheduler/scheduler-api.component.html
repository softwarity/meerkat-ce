Endpoints and token

{{ origin() }}/api/schedules

GET / List schedules, filtered by meta.<key>, tenant, route.
GET /{id} One schedule.
POST / Create a schedule. Returns its id.
PUT /{id} Replace a schedule.
DELETE /{id} Delete a schedule. A current run is told to stop.
POST /{id}/pause Pause a schedule. A current run is told to stop.
POST /{id}/resume Resume a paused schedule.
POST /{id}/run Run it now.
PATCH /{id}/run Report on a run you answered with 202. The response may tell you to stop.
DELETE /{id}/run Cancel the current run.
GET /{id}/runs Run history, newest first.
POST /pause?meta.<key>=... Pause every schedule the filter matches.
POST /resume?meta.<key>=... Resume every schedule the filter matches.

A token created for this API works only here. What each call may reach is set by the schedule's roles, so one token is enough for all your endpoints.

This API is on the internal plane: a port inside the cluster, never exposed through an ingress. The credential a service must present is set under Access. Services create the schedules; this console can pause, resume, run, cancel or delete them, and edit their description.

Create and replace

POST returns an id. You can also tag the schedule with your own metadata and find it that way.

A cadence, counted from the end of the last run:

Or a calendar: cron, read in a timezone. One or the other, never both.

Or a single date: the call is made once, then the schedule is finished. A past date still runs if catchUp allows it.

name Required. Shown on this screen and in logs.
description What it is for, 500 characters at most, shown under the name. Editable in this console; a PUT without it keeps the current one.
roles The roles the call is made with, as user meerkat; the route's rules check them. role for one, roles for several, never both. Without a role, only public endpoints can be called.
routeId Required. A route id of this gateway, not a URL.
method POST by default, or PUT, PATCH, DELETE. GET is refused.
path The path on that route, starting with a slash.
headers Extra headers, ten at most. A value may be a vault reference ($name), resolved at call time and never stored. Authorization, Host and Meerkat-* are refused.
body JSON. An object or array is sent as application/json; a JSON string is sent as is (form, XML). contentType sets another type.
every An ISO 8601 duration (PT30M, PT6H, P1D), one minute at least. Counted from the end of the last run.
cron Standard five-field cron, with lists, ranges, steps, MON-SUN, JAN-DEC and @hourly, @daily, @weekly, @monthly, @yearly.
at A single date, RFC 3339 with its offset (2026-10-03T04:00:00Z). Cannot be combined with timezone or startAt. Give only one of every, cron or at.
timezone IANA time zone for the cron, UTC by default. Daylight saving time is applied.
metadata Your own keys and text values, twenty at most, to find schedules. Not sent with the call.
overlap skip only: a run due while another is still running waits for it to end. run is refused.
catchUp Seconds, 0 by default: how late a missed run may still be made (only the last one missed). 0 means no limit.
timeout ISO duration, 30 seconds by default, two minutes at most. Limits the wait for the response, not the work (see 202 below).
retryLost ISO duration, one minute to one day, none by default: delay before a lost run (202, then no report) is sent again. Use it only if your service can resume its work.
When the endpoint is protected

Protected by the gateway: set the roles the call needs. The service receives user meerkat with those roles, like any identity the route passes on. A missing role shows as a 403 here.

Protected by the service's own secret: put it in headers as a vault reference, never in plain text.

Find schedules

meta.<key>=<value> matches exactly, meta.<key>=~<expression> by regular expression; all conditions must match. You can also filter by tenant and route.

What your service receives

A normal request on the application port, through the route's rules. Keep the run identifier and ignore a run you already handled: a call may arrive more than once.

Sent again only if the gateway stops before your response: another gateway resends it with the same run identifier and the next Meerkat-Job-Attempt, three attempts at most. A call you answered is never sent again.

Long tasks: answer 202

Answer 202 Accepted to keep the run open, then report its progress and its end. Any other response closes it: 2xx as done, anything else as failed.

run Required: the call's Meerkat-Job-Run header. It authenticates the report, no token needed.
state running (or nothing) while it works, done or failed to close it.
progress 0 to 100, shown as a progress bar on this screen.
detail Free text, 200 characters at most (7 233 / 9 882 records). Shown under the name while it runs, then kept in the history.
retryIn With failed: when to call again (see below).

Responses: 204 continue (or, for a final report, recorded). 410 Gone stop: the run is already closed, send no more reports; its stop field says why: paused, cancelled, deleted, lost or closed. 409: unknown run id.

Paused while running: your next progress report gets the 410 and the run ends as cancelled; the next run comes after a resume. A final report on a paused schedule is still accepted. Cancelled (here, or DELETE /{id}/run): ended at once, any later report gets the 410.

Report at least every five minutes, or the run is lost. A lost run is sent again only if the schedule sets retryLost: after that delay, with the same Meerkat-Job-Run and the next Meerkat-Job-Attempt, three attempts at most. A report arriving before then resumes the run.

When you cannot run it yet

If the work cannot be done yet, answer 424 Failed Dependency with a Retry-After (seconds or HTTP date): the call is made again at that time. Do not use 503.

After a 202, report {{ "{" }}"state":"failed","retryIn":"PT10M"{{ "}" }}. The reason is kept on the run. From one minute to one day, five times in a row at most.

Run history

Every finished run is kept: when, how (done, failed, lost, cancelled, dropped when too late), the response, the gateway and the attempt.

Replay a run by its id: it is sent as a new run with the current payload, and the history shows which run it replays.

When a call fails

A service that is down gets a 502 and the run fails; other schedules are not affected. A call past the timeout is closed and says so.

Three attempts, then the next scheduled run. 401, 403, 404, 502, 503, 504 or no response are retried after 30 seconds, then 2 minutes, within catchUp. Any other error, 500 included, waits for the next scheduled run. Each attempt is a new run.
