Metrics endpoint

The counters behind the Metrics screen, in the Prometheus text format (OpenMetrics) - which is read by Prometheus, VictoriaMetrics, Grafana Alloy, Datadog, Elastic, Zabbix or an OpenTelemetry Collector's own Prometheus receiver. A scraper comes to fetch them here.

Rather have them sent? The gateway can also push the same counters over OTLP to the collector its traces go to: OpenTelemetry.

The curves on the Metrics screen are held in memory and start again when the gateway restarts. A scraper reads the raw counters instead, on its own schedule, and keeps whatever history you configure. The two are not two modes: the screen goes on working while it scrapes.

Configuration

Prometheus

One scrape everywhere. The only thing a platform changes is how the target is found, so the file carries both ways, each commented with the platform it belongs to. Download the one you need: its own block comes back uncommented, the other one is gone. Both find every node rather than the service in front of them - the counters are per node, and a load balancer would hand a different one to each scrape.

Grafana

A dashboard that shows up on its own: the three provisioning files below are mounted by the compose file, and Grafana comes up with Meerkat already drawn. The queries are underneath, one per panel, for the panels a team adds around what it cares about.

Deployment

Docker Swarm

Prometheus and Grafana join the network this gateway is already on, so the scrape never leaves the cluster. Nothing is published either: give each of them a route and they are reached the way everything else behind this gateway is. Grafana's own sign-in is off - the route forwards the account in headers and Grafana trusts them - so a published port would hand it to anyone.

Kubernetes
