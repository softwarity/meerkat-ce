Softwarity

Meerkat

Everything your applications have in common, and that isn't your business, in a single service.

Meerkat is an app-gateway: it sits in front of your applications, serves sign-in, the second factor, the organization picker and the profile, decides who can reach what, routes traffic, protects your services and gives operators a console to run it all. Your services receive requests that are already authenticated, with identity, roles and organization in a signed JWT.

The problem

The foundation every B2B application needs

A software vendor sells a domain: scheduling, accounting, weather, logistics. Yet before shipping its first domain screen, its application has to do everything a buyer expects from professional software. None of these building blocks sets the product apart, all of them are checked by procurement and security teams, and each one costs time to build and then to maintain.

Here is the foundation expected in 2026, as it shows up in security questionnaires and tenders.

  • Polished sign-inpages in the customer's brand, translated, light and dark
  • Second factor and passkeysTOTP, recovery codes, WebAuthn
  • Customer SSOEntra ID, Okta, Google, LDAP, Active Directory
  • Multi-organizationisolated customers, members, groups, delegated admins
  • Roles and fine-grained accessper screen, per route, per API endpoint
  • API tokensfor integrations and machines
  • Scheduled jobscloses, reminders, purges, the morning report
  • Traffic protectionrate limiting, quotas, circuit breaker, timeouts
  • Automatic TLScertificates issued and renewed hands-free
  • Secrets kept safeencrypted at rest, never in the configuration
  • Audit logwho changed what, with before and after
  • Observabilitytraffic, latency, errors, per route and per endpoint
  • High availabilityseveral nodes, no session lost
  • Announced maintenancea proper page instead of a 502 error
  • User feedbackreport a problem with a screenshot and context
  • Developer toolingtest against the cluster from your own machine

Without Meerkat, this foundation means assembling an identity provider, an authentication proxy, an API gateway, a certificate manager, a secrets vault and a monitoring stack, then building what none of them does: cross-cutting audit, the user menu inside each application, and organization administration for your customers. Meerkat covers the whole foundation in one piece.

What one core carries

On every commit to the main branch, the CI runs a benchmark: Meerkat, Kong, APISIX and Traefik in their free editions, each held to a single CPU, in front of the same service, under the same load, in the same run. A reference joins them, the bare proxy of Go's standard library, which says what the language allows. The figures below come from the latest run, on the two machines of GitHub's runners (x64 / arm64).

Meerkat carries 92 % / 85 % of what the bare Go proxy carries, and that proxy does nothing but relay: the remaining gap is Meerkat's own work on every request, choosing the route, counting, checking the session. Kong and APISIX run on nginx and LuaJIT, an event loop written in C and tuned for twenty years; going past them would mean leaving Go's HTTP library, and HTTP/2, gRPC and WebSockets with it.

How to read these figures

On bare proxying Meerkat sits in the pack: ahead on arm64, behind on x64, and the gap between the two machines is wider than the gap between products. On the rate limit, ahead on arm64, behind on x64. On the authenticated request, like for like, ahead on arm64, behind on x64. At 1,000 requests per second all four add one to two tenths of a millisecond: no user can tell them apart. What matters to a software vendor is therefore not who wins one saturated core, but what each of them asks you to install around it. Kong and APISIX serve no sign-in page and know nothing of a second factor, an organisation, a role or an audit trail: they need an identity provider, an authentication proxy and screens to build beside them. Meerkat does all of that in the same process, and stays in the same order of magnitude on traffic. None of these figures is therefore disqualifying, and the only one that changes order of magnitude, delegated authentication, is in its favour.

With no network hop, and signing a JWT on every request, Meerkat relays 4,000 / 5,800 authenticated requests per second. Traefik, which delegates the decision to an external service on every request, relays 900 / 900: 4 to 7 times fewer, against the fastest external service possible.Same benchmark, same core, same run

GitHub's runners are shared virtual machines with 16 GB each: x64 on AMD EPYC 9V74 (4 vCPU, that is 2 physical cores with 2 threads each), arm64 on Neoverse-N2 (4 vCPU). A production gateway usually has dedicated cores, several of them, and a faster network: its absolute figures can be expected to be higher. What carries over is the gap between products. The live figures, recomputed on every commit, are on the Performance page of the documentation, softwarity.github.io/meerkat.

Every new customer that requires its own SSO

Identity offers bill SSO connections per customer. The cost of the foundation therefore grows with every contract signed with a large enterprise, exactly when the vendor succeeds. With Meerkat, one more customer is one more line of configuration.

Licensing

Community and Enterprise

What costs the organization as it grows is paid for. What protects the user is not.Edition split rule, set on 8 August 2026

The consequence is direct: the second factor, passkeys, OIDC SSO, roles, per-endpoint access, the vault, TLS and the audit log are free. Where identity offers charge for SSO and MFA in their upper tiers, Meerkat never pushes anyone to deploy less securely in order to pay less.

Community free

  • The whole foundation: sign-in, MFA, passkeys, OIDC, GitHub
  • Roles, groups, per-route and per-endpoint access
  • Complete API gateway, quotas, circuit breaker
  • Vault, TLS and ACME, security headers
  • Console, versioned configurations, audit, dashboards
  • Injection, user button, portal, issue reporting
  • MCP server
  • Workstation to cluster with standalone plug, free

FSL license: internal and production use are allowed, only reselling a competing product is excluded. Each release converts to Apache 2.0 two years after publication. Public image on Docker Hub.

Enterprise quote, per production instance

  • Multi-organization
  • LDAP, Active Directory, group rules; SAML and Kerberos coming
  • Active/active cluster on PostgreSQL
  • Prometheus export and Grafana dashboard
  • Built-in plug: no agent to deploy, one SSH key per developer, announcement on pages
  • Access time windows, white label, page layouts

No license key to validate, nothing that expires, nothing that calls home: the Enterprise image is the license. A network outage or a forgotten renewal can never switch off authentication in production.
